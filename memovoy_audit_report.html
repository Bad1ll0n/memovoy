Secção 2 — Modelação e Schema Design §2

🔴 CRÍTICO fn_validate_prompt_traffic — race condition em concorrência
A função valida que SUM(traffic_percentage) = 100 fazendo um SELECT antes do INSERT/UPDATE. Em concorrência (dois admins a alterar simultaneamente), ambas as transacções lêem o estado anterior, validam com sucesso, e o resultado final pode ser 120% ou 80%. Não há lock na leitura.

Fix: usar SERIALIZABLE transaction isolation ou SELECT ... FOR UPDATE na validação. 
-- Fix: adicionar lock exclusivo antes da validação
CREATE OR REPLACE FUNCTION fn_validate_prompt_traffic()
RETURNS TRIGGER AS $$
DECLARE
  total_pct INTEGER;
BEGIN
  -- Lock advisory para serializar actualizações de traffic_percentage
  PERFORM pg_advisory_xact_lock(hashtext('prompt_versions_traffic'));

  SELECT COALESCE(SUM(traffic_percentage), 0)
  INTO total_pct
  FROM prompt_versions
  WHERE is_active = true
    AND (TG_OP = 'INSERT' OR id != NEW.id);

  IF total_pct + NEW.traffic_percentage != 100 THEN
    RAISE EXCEPTION 'Soma de traffic_percentage deve ser 100. Actual: %, novo: %',
      total_pct, NEW.traffic_percentage;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
🔴 CRÍTICO fn_protect_db_region — current_setting() pode retornar '' em contexto system/cron
O trigger usa current_setting('app.current_user_role', true) para verificar se é admin. Em jobs de sistema, cron jobs, ou migrations, esta variável não está definida e retorna NULL ou ''. A condição NOT IN ('admin') com NULL é sempre FALSE em SQL, o que significa que qualquer job de sistema pode alterar o role de qualquer utilizador sem restrição. É um bypass silencioso de segurança. 
-- Fix: tratar explicitamente NULL/'' como não-admin
CREATE OR REPLACE FUNCTION fn_protect_db_region()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.db_region != OLD.db_region THEN
    RAISE EXCEPTION 'db_region é imutável após registo.';
  END IF;

  IF NEW.role != OLD.role THEN
    -- Verificar explicitamente — COALESCE para tratar NULL como 'user'
    IF COALESCE(current_setting('app.current_user_role', true), '') != 'admin' THEN
      RAISE EXCEPTION 'Apenas admins podem alterar o role. Role actual de sessão: "%"',
        COALESCE(current_setting('app.current_user_role', true), '(não definido)');
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
🔴 CRÍTICO RLS policies com current_setting() — bypass quando variável não está definida
Todas as policies RLS usam current_setting('app.current_user_id', true)::UUID. Quando a variável não está definida, o segundo argumento true faz retornar NULL. NULL::UUID lança um erro de cast em algumas versões, mas em outras retorna NULL silenciosamente. Pior: se o service account usar BYPASSRLS mas esquecer de definir a variável, não há fallback seguro. É necessário um default seguro explícito. 
-- Criar função helper para extrair user_id de sessão de forma segura
CREATE OR REPLACE FUNCTION current_user_id()
RETURNS UUID AS $$
DECLARE
  v_id TEXT;
BEGIN
  v_id := current_setting('app.current_user_id', true);
  IF v_id IS NULL OR v_id = '' THEN
    RETURN NULL;  -- policy que usa IS NOT DISTINCT FROM NULL vai bloquear tudo
  END IF;
  RETURN v_id::UUID;
END;
$$ LANGUAGE plpgsql STABLE SECURITY DEFINER;

-- Re-criar policies usando a função helper:
-- USING (id = current_user_id())  em vez de current_setting(...)::UUID directo
🔴 CRÍTICO itinerary_collaborators — sem RLS para INSERT e DELETE
A policy itinerary_collaborators_own só cobre FOR SELECT. Não há policies para INSERT, UPDATE e DELETE. Qualquer utilizador autenticado pode adicionar-se como colaborador de qualquer roteiro alheio directamente via API, ou remover colaboradores de roteiros que não são seus. Com RLS activo, operações sem policy correspondente são bloqueadas por defeito — o que significa que actualmente nenhum convite funciona para utilizadores normais. 
-- Policies em falta para itinerary_collaborators

-- Só o dono do roteiro pode convidar colaboradores
CREATE POLICY itinerary_collaborators_insert ON itinerary_collaborators
  FOR INSERT
  WITH CHECK (
    itinerary_id IN (
      SELECT id FROM itineraries
      WHERE user_id = current_user_id()
    )
  );

-- Colaborador pode aceitar o seu próprio convite (UPDATE accepted_at)
CREATE POLICY itinerary_collaborators_accept ON itinerary_collaborators
  FOR UPDATE
  USING (user_id = current_user_id());

-- Dono pode remover; colaborador pode sair
CREATE POLICY itinerary_collaborators_delete ON itinerary_collaborators
  FOR DELETE
  USING (
    user_id = current_user_id()
    OR itinerary_id IN (
      SELECT id FROM itineraries
      WHERE user_id = current_user_id()
    )
  );
🟠 ALTO reactions — sem FK para posts/comments (integridade referencial polimórfica)
A tabela reactions usa um padrão polimórfico (target_type + target_id) sem FK declarada. É possível inserir uma reação para um target_id que não existe em nenhuma tabela — os triggers de contador vão incrementar um contador num registo inexistente ou falhar silenciosamente. A CHECK constraint apenas valida o tipo, não a existência do alvo.

Fix recomendado: trigger de validação de existência, ou migrar para tabelas separadas post_reactions e comment_reactions com FK real. 
-- Opção A: trigger de validação de existência (sem alterar o schema)
CREATE OR REPLACE FUNCTION fn_validate_reaction_target()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.target_type = 'post' THEN
    IF NOT EXISTS (SELECT 1 FROM posts WHERE id = NEW.target_id AND deleted_at IS NULL) THEN
      RAISE EXCEPTION 'Post % não existe', NEW.target_id;
    END IF;
  ELSIF NEW.target_type = 'comment' THEN
    IF NOT EXISTS (SELECT 1 FROM comments WHERE id = NEW.target_id AND deleted_at IS NULL) THEN
      RAISE EXCEPTION 'Comentário % não existe', NEW.target_id;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_reaction_target
  BEFORE INSERT ON reactions
  FOR EACH ROW EXECUTE FUNCTION fn_validate_reaction_target();
🟠 ALTO reports — mesmo padrão polimórfico sem FK
Mesmo problema de reactions: target_id em reports não tem FK para nenhuma tabela. É possível criar uma denúncia para um UUID inventado, que nunca será encontrado na fila de moderação mas ocupa espaço e distorce métricas. 
-- Fix: trigger de validação semelhante ao de reactions
CREATE OR REPLACE FUNCTION fn_validate_report_target()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.target_type = 'post'
    AND NOT EXISTS (SELECT 1 FROM posts WHERE id = NEW.target_id)
  THEN
    RAISE EXCEPTION 'Conteúdo denunciado não existe: % / %', NEW.target_type, NEW.target_id;
  END IF;
  -- Idem para 'comment' e 'profile'
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_report_target
  BEFORE INSERT ON reports
  FOR EACH ROW EXECUTE FUNCTION fn_validate_report_target();
🟠 ALTO leaderboard_entries — UNIQUE com scope_id nullable pode permitir duplicados
O constraint UNIQUE(user_id, leaderboard_type, scope_id, period_start) com scope_id nullable tem um comportamento subtil em PostgreSQL: NULL != NULL nos índices UNIQUE, o que significa que é possível inserir múltiplas entradas globais (scope_id NULL) para o mesmo utilizador e período. O constraint não protege contra isso. 
-- Fix: índice UNIQUE com NULLS NOT DISTINCT (PostgreSQL 15+)
ALTER TABLE leaderboard_entries
  DROP CONSTRAINT leaderboard_unique_entry;

CREATE UNIQUE INDEX leaderboard_unique_entry
  ON leaderboard_entries(user_id, leaderboard_type, period_start)
  NULLS NOT DISTINCT
  -- scope_id NULL = leaderboard global → deve ser único por (user, type, period)
  WHERE scope_id IS NULL;

CREATE UNIQUE INDEX leaderboard_unique_entry_scoped
  ON leaderboard_entries(user_id, leaderboard_type, scope_id, period_start)
  WHERE scope_id IS NOT NULL;
🟡 MÉDIO itinerary_days — falta constraint de consistência de datas
A coluna date em itinerary_days não tem constraint que a obrigue a estar dentro do intervalo [start_date, end_date] do roteiro pai. É possível criar um dia com uma data completamente fora do roteiro, corrompendo a estrutura silenciosamente. 
-- Trigger de validação de data do dia vs intervalo do roteiro
CREATE OR REPLACE FUNCTION fn_validate_day_date()
RETURNS TRIGGER AS $$
DECLARE
  v_start DATE; v_end DATE;
BEGIN
  SELECT start_date, end_date INTO v_start, v_end
  FROM itineraries WHERE id = NEW.itinerary_id;

  IF NEW.date < v_start OR NEW.date > v_end THEN
    RAISE EXCEPTION
      'Data do dia (%) fora do intervalo do roteiro [%, %]',
      NEW.date, v_start, v_end;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_day_date
  BEFORE INSERT OR UPDATE ON itinerary_days
  FOR EACH ROW EXECUTE FUNCTION fn_validate_day_date();
🟡 MÉDIO user_profiles.countries_visited — pode dessincronizar de total_countries
countries_visited é um array de CHAR(2) e total_countries é um INTEGER desnormalizado calculado a partir desse array. Se alguém actualizar countries_visited directamente (sem passar pelo trigger do roteiro), total_countries fica dessincronizado. O trigger fn_update_trip_stats actualiza ambos, mas não há constraint que garanta total_countries = array_length(countries_visited, 1).
🟡 MÉDIO Enums como VARCHAR vs tipo ENUM nativo
Campos como status, role, visibility, group_type, platform etc. são VARCHAR com CHECK constraints. Funciona correctamente, mas tipos ENUM nativos do PostgreSQL oferecem: melhor performance (armazenamento interno como inteiro), validação automática sem CHECK, e documentação de schema mais clara. O custo é que alterar um ENUM requer ALTER TYPE em vez de apenas actualizar o CHECK.
Contexto: para uma aplicação em evolução activa, VARCHAR + CHECK é a escolha pragmática correcta. Esta é uma sugestão, não uma correcção.

Secção 3 — Performance e Índices §3

🟠 ALTO itinerary_summary VIEW — GROUP BY com múltiplos LEFT JOINs causa N² de rows
A view faz COUNT(DISTINCT idays.id) e COUNT(DISTINCT iact.id) com dois LEFT JOINs sem filtro de linha eficiente. Para um roteiro com 7 dias e 5 atividades por dia (35 actividades), o produto cartesiano antes do GROUP BY é 7×35=245 linhas. A 100M roteiros, queries a esta view sem LIMIT vão degradar severamente. Deve ser materializada ou simplificada. 
-- Substituir por MATERIALIZED VIEW refrescada periodicamente
CREATE MATERIALIZED VIEW itinerary_summary_mat AS
-- ... (mesmo SQL da view actual) ...
WITH DATA;

-- Índice único para refresh CONCURRENTLY
CREATE UNIQUE INDEX ON itinerary_summary_mat(id);

-- Refrescar após publicação de roteiro (trigger ou job)
-- REFRESH MATERIALIZED VIEW CONCURRENTLY itinerary_summary_mat;

-- Alternativa mais leve: subqueries correlacionadas
CREATE OR REPLACE VIEW itinerary_summary AS
SELECT
  i.*,
  up.display_name, up.avatar_url,
  ic.total_kg_co2, ic.vs_avg_pct,
  (SELECT COUNT(*) FROM itinerary_days WHERE itinerary_id = i.id)          AS days_count,
  (SELECT COUNT(*) FROM itinerary_activities ia
   JOIN itinerary_days d ON d.id = ia.day_id
   WHERE d.itinerary_id = i.id AND ia.deleted_at IS NULL)    AS activities_count
FROM itineraries i
JOIN user_profiles up ON up.user_id = i.user_id
LEFT JOIN itinerary_carbon ic ON ic.itinerary_id = i.id
WHERE i.status = 'published' AND i.deleted_at IS NULL;
🟠 ALTO top_countries_month VIEW — usa NOW() o que impede caching do plan
A view usa DATE_TRUNC('month', NOW()) directamente. Isto é um valor não-determinístico que impede o PostgreSQL de reutilizar planos de execução em cache. Para uma query executada milhares de vezes por hora (homepage), o overhead de replanning é significativo. Deve ser parametrizada ou os resultados pré-calculados. 
-- Função com parâmetro de data para caching correcto
CREATE OR REPLACE FUNCTION get_top_countries(p_month DATE DEFAULT DATE_TRUNC('month', NOW()))
RETURNS TABLE(country_code CHAR(2), trip_count BIGINT, unique_travelers BIGINT) AS $$
  SELECT
    i.country_code,
    COUNT(*)                    AS trip_count,
    COUNT(DISTINCT i.user_id)   AS unique_travelers
  FROM itineraries i
  WHERE
    i.status = 'published'
    AND i.deleted_at IS NULL
    AND i.published_at >= p_month
    AND i.published_at <  p_month + INTERVAL '1 month'
  GROUP BY i.country_code
  ORDER BY trip_count DESC
  LIMIT 10;
$$ LANGUAGE SQL STABLE;
🟡 MÉDIO feed_interactions — índice composto (user_id, post_id) em falta
O índice idx_feed_interactions_user cobre (user_id, created_at DESC) mas a query de ML mais comum é "todas as interacções de um utilizador com um post específico" — por exemplo, verificar se já deu skip. Sem índice composto em (user_id, post_id), esta query faz scan no chunk activo por utilizador. 
CREATE INDEX CONCURRENTLY idx_feed_interactions_user_post
  ON feed_interactions(user_id, post_id, interaction_type, created_at DESC);
🟡 MÉDIO posts — índice de feed global em falta (para descoberta)
Existem índices para posts por utilizador e por país, mas não para o feed de descoberta global (posts públicos recentes de qualquer utilizador, ordenados por data ou popularidade). Este é o feed que serve utilizadores novos antes de seguirem alguém. 
CREATE INDEX CONCURRENTLY idx_posts_global_feed
  ON posts(created_at DESC, likes_count DESC)
  WHERE deleted_at IS NULL
    AND is_hidden = false
    AND visibility = 'public';
🟡 MÉDIO user_sessions — sem índice em is_suspicious para anomaly detection queries
O dashboard de segurança e o job de envio de alertas vai querer listar todas as sessões suspeitas activas. Sem índice, é seq scan em toda a tabela. 
CREATE INDEX CONCURRENTLY idx_sessions_suspicious
  ON user_sessions(user_id, created_at DESC)
  WHERE is_suspicious = true
    AND revoked_at IS NULL;
🟢 SUGESTÃO idx_crowding_geo_hash — redundante com a PRIMARY KEY
O índice idx_crowding_geo_hash ON location_crowding_stats(location_geo_hash) é um subconjunto da PRIMARY KEY (location_geo_hash, day_of_week, hour_of_day). O PostgreSQL já usa a PK para lookups por location_geo_hash como prefixo. Este índice é redundante e ocupa espaço desnecessário. 
-- Remover índice redundante:
DROP INDEX idx_crowding_geo_hash;
🟢 SUGESTÃO Índice de cobertura para o perfil público
A query de perfil público (username lookup + dados básicos) faz join entre users e user_profiles. Um índice de cobertura em users pode eliminar o heap fetch para esta query crítica. 
CREATE INDEX CONCURRENTLY idx_users_profile_lookup
  ON users(username)
  INCLUDE (id, role, is_private, is_verified, follower_count)
  WHERE deleted_at IS NULL;

Secção 4 — Segurança e Permissões §4

🟠 ALTO Roles de base de dados não definidos nas migrations
As migrations não criam roles PostgreSQL separados para o API layer (memovoy_api), o serviço de analytics (memovoy_analytics, read-only), e migrations (memovoy_migrations). Se a aplicação usa o superuser por omissão, qualquer injecção SQL bem-sucedida tem privilégios totais, incluindo DROP TABLE e acesso a todas as bases de dados. 
-- Adicionar a V12 ou executar manualmente em produção:
CREATE ROLE memovoy_api LOGIN PASSWORD '...';
CREATE ROLE memovoy_analytics LOGIN PASSWORD '...';
CREATE ROLE memovoy_migrations LOGIN PASSWORD '...';

-- API: leitura/escrita nas tabelas de dados, sem DDL
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO memovoy_api;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO memovoy_api;
ALTER ROLE memovoy_api SET search_path = public;

-- Analytics: só leitura
GRANT SELECT ON ALL TABLES IN SCHEMA public TO memovoy_analytics;

-- Migrations: DDL completo mas não superuser
GRANT ALL ON SCHEMA public TO memovoy_migrations;
GRANT BYPASSRLS TO memovoy_migrations;  -- necessário para executar migrations
🟡 MÉDIO mfa_secret_encrypted — sem validação de que está preenchido quando mfa_enabled = true
Um utilizador pode ter mfa_enabled = true e mfa_secret_encrypted = NULL simultaneamente. A autenticação MFA vai falhar silenciosamente ou deixar o utilizador sem MFA funcional apesar de a flag estar activa. 
ALTER TABLE users
  ADD CONSTRAINT users_mfa_secret_required
  CHECK (
    mfa_enabled = false
    OR (mfa_enabled = true AND mfa_secret_encrypted IS NOT NULL)
  );
🟡 MÉDIO audit_logs — sem particionamento por data
audit_logs é append-only e vai crescer indefinidamente. A 100M utilizadores, cada acção gera um registo — podem ser centenas de milhões de linhas por ano. Sem particionamento por data, compliance queries (RGPD: "todas as acções do utilizador X") vão degradar ao longo do tempo. Recomenda-se TimescaleDB hypertable ou particionamento nativo por mês. 
-- Converter audit_logs em hypertable (mesma abordagem de feed_interactions)
-- Requer que a PK inclua created_at primeiro:
ALTER TABLE audit_logs DROP CONSTRAINT audit_logs_pkey;
ALTER TABLE audit_logs ADD PRIMARY KEY (id, created_at);

SELECT create_hypertable('audit_logs', 'created_at',
  chunk_time_interval => INTERVAL '1 month',
  if_not_exists => TRUE);

-- Retenção: comprimir chunks com mais de 1 ano
SELECT add_retention_policy('audit_logs', INTERVAL '7 years'); -- RGPD: 7 anos
🟢 SUGESTÃO push_token — armazenado em plaintext
Os tokens FCM/APNs em user_devices.push_token estão em plaintext. Não são dados pessoais directos (não identificam uma pessoa sem contexto adicional), mas um leak da tabela expõe todos os tokens e permite envio de notificações maliciosas a todos os dispositivos. Considerar encriptação simétrica (pgcrypto) ou armazenamento num vault externo.

Secção 5 — Qualidade dos Dados §5

🟠 ALTO trip_expenses — sem constraint de consistência itinerary_id + user_id
Um utilizador pode registar um gasto num roteiro que não lhe pertence e do qual não é colaborador, simplesmente especificando um itinerary_id arbitrário. O RLS protege a leitura mas não o INSERT. Falta verificar que o user_id do gasto pertence ao roteiro. 
-- Trigger de validação de ownership antes de inserir gasto
CREATE OR REPLACE FUNCTION fn_validate_expense_ownership()
RETURNS TRIGGER AS $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM itineraries
    WHERE id = NEW.itinerary_id
      AND (
        user_id = NEW.user_id
        OR EXISTS (
          SELECT 1 FROM itinerary_collaborators ic
          WHERE ic.itinerary_id = NEW.itinerary_id
            AND ic.user_id = NEW.user_id
            AND ic.accepted_at IS NOT NULL
        )
      )
  ) THEN
    RAISE EXCEPTION 'Utilizador não tem acesso ao roteiro %', NEW.itinerary_id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_validate_expense_ownership
  BEFORE INSERT ON trip_expenses
  FOR EACH ROW EXECUTE FUNCTION fn_validate_expense_ownership();
🟡 MÉDIO itinerary_activities — position não é UNIQUE por day_id
Duas actividades no mesmo dia podem ter a mesma position. Há uma CHECK constraint que valida position >= 1, mas não há UNIQUE constraint em (day_id, position). O drag-and-drop da UI pode criar colisões de posição que causam ordenação inconsistente. 
-- Adicionar UNIQUE (day_id, position) com índice parcial (excluindo soft-deleted)
CREATE UNIQUE INDEX idx_activities_day_position_unique
  ON itinerary_activities(day_id, position)
  WHERE deleted_at IS NULL;
🟡 MÉDIO post_media — falta UNIQUE (post_id, position)
Mesmo problema: dois media do mesmo post podem ter a mesma posição, causando ordem de exibição indeterminada. 
CREATE UNIQUE INDEX idx_post_media_position_unique
  ON post_media(post_id, position);
🟢 SUGESTÃO currency em trip_expenses — sem validação ISO 4217
O campo currency CHAR(3) não tem CHECK constraint. Qualquer string de 3 caracteres é aceite. Considerar CHECK com lista dos principais códigos ou tabela de lookup de moedas. 
ALTER TABLE trip_expenses
  ADD CONSTRAINT trip_expenses_currency_format
  CHECK (currency ~ '^[A-Z]{3}$');  -- formato ISO 4217: 3 letras maiúsculas
🟢 SUGESTÃO country_code sem validação de formato
CHAR(2) aceita qualquer dois caracteres. Um CHECK regex simples garante conformidade com ISO 3166-1 alpha-2 sem necessitar de tabela de lookup. 
-- Adicionar nas tabelas users, itineraries, posts
ALTER TABLE users
  ADD CONSTRAINT users_country_code_format
  CHECK (country_code IS NULL OR country_code ~ '^[A-Z]{2}$');

Top 5 Prioridades

1
Corrigir policies RLS em falta para itinerary_collaborators
Com RLS activo e sem policies INSERT/UPDATE/DELETE, nenhum convite funciona para utilizadores normais. Impacto funcional imediato em produção. Fix em 30 minutos, zero downtime.
2
Criar helper current_user_id() e corrigir fn_protect_db_region
O bypass silencioso de segurança quando app.current_user_role não está definido é um risco real em jobs e migrations. Pode resultar em alterações de role sem autorização. Fix em 20 minutos.
3
Criar roles PostgreSQL separados (memovoy_api, memovoy_analytics)
Sem roles separados, a aplicação provavelmente usa o owner/superuser. Qualquer injecção SQL bem-sucedida tem privilégios totais. É a medida de defesa em profundidade mais impactante possível.
4
Adicionar triggers de validação polimórfica (reactions + reports)
Os padrões polimórficos sem FK permitem inserir reações e denúncias para IDs inexistentes, corrompendo contadores e filas de moderação. Fix simples com dois triggers.
5
Optimizar itinerary_summary VIEW ou materializar
O produto cartesiano latente na view vai degradar linearmente com o crescimento. Deve ser abordado antes de atingir 1M de roteiros publicados.
