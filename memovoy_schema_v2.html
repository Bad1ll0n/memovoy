Metodologia: li o schema completo linha a linha, cruzei cada referência de FK com a tabela alvo, validei cada índice parcial quanto à sua viabilidade no PostgreSQL, e verifiquei a consistência entre a "visão geral" e as tabelas realmente definidas.

Tabelas em falta — 7 problemas

✗ #1 — Tabela comments ausente
O domínio Social lista "comments" e a funcionalidade existe no produto, mas a tabela nunca foi definida. Sem ela, nenhum comentário pode ser armazenado. Inclui parent_comment_id para respostas aninhadas.
✓ Corrigido — tabela definida no tab Social
✗ #2 — Tabela user_badges ausente mas referenciada
A tabela challenges tem uma FK para user_badges (badge_id) mas essa tabela nunca foi definida. Isto causaria um erro imediato no CREATE TABLE challenges. A tabela de badges precisa de existir antes.
✓ Corrigido — badges definidos no tab Gamificação
✗ #3 — Tabela notifications ausente
O sistema de notificações (push, email, geo contextuais, resumo do dia seguinte) não tem tabela para persistir notificações pendentes e histórico. Sem ela, notificações não entregues não podem ser reenviadas.
✓ Corrigido — tabela definida no tab Sistema
✗ #4 — Tabela audit_logs ausente
Obrigatória por RGPD/LGPD — registo de todas as ações sobre dados pessoais (acesso, exportação, deleção). Sem ela, não é possível provar compliance em caso de auditoria regulatória.
✓ Corrigido — tabela definida no tab Sistema
✗ #5 — Tabela feature_flags ausente
O roadmap define feature flags como mecanismo central de lançamento faseado mas não há tabela para as gerir. Sem ela, as flags têm de ser hard-coded no código — impossível de alterar sem deploy.
✓ Corrigido — tabela definida no tab Sistema
✗ #6 — Tabela leaderboard_entries ausente
Listada no domínio de gamificação mas nunca definida. Necessária para os top países do mês e rankings de desafios.
✓ Corrigido — tabela definida no tab Gamificação
✗ #7 — Tabela user_devices ausente
Listada no domínio de utilizadores mas nunca definida. Necessária para push notifications (armazenar FCM/APNs tokens) e para o anomaly detection por device.
✓ Corrigido — tabela definida no tab Utilizadores

Constraints em falta — 4 problemas

✗ #8 — follows sem CHECK contra auto-follow
Nada impede um utilizador de seguir-se a si próprio (follower_id = following_id). Isto corromperia o feed e os contadores.
✓ Corrigido — CHECK(follower_id != following_id) adicionado
✗ #9 — itinerary_days sem UNIQUE constraint
A unicidade de (itinerary_id, day_number) estava mencionada na nota mas não definida como constraint. Dois dias com o mesmo número num roteiro seriam possíveis, corrompendo a estrutura.
✓ Corrigido — UNIQUE(itinerary_id, day_number) adicionado
✗ #10 — reports sem UNIQUE constraint
A unicidade de (reporter_id, target_id, target_type) estava mencionada na nota mas não definida como constraint. Um utilizador poderia denunciar o mesmo conteúdo múltiplas vezes, inflacionando o sistema.
✓ Corrigido — UNIQUE(reporter_id, target_id, target_type) adicionado
✗ #11 — prompt_versions.traffic_percentage sem validação de soma
Sem controlo, as percentagens podiam somar 120% ou 80%, distribuindo tráfego incorretamente no A/B testing. Uma CHECK constraint por linha não chega — é preciso uma trigger que valide a soma de todas as versões ativas.
✓ Corrigido — trigger de validação de soma adicionada no tab Triggers

Índices errados ou ausentes — 3 problemas

✗ #12 — Índice com condição dinâmica (NÃO FUNCIONA em PostgreSQL)
CREATE INDEX ... WHERE created_at > NOW() - INTERVAL '90 days' usa NOW() que é não-determinístico. PostgreSQL exige que condições de índices parciais sejam imutáveis. Este índice daria erro no CREATE e nunca seria criado.
✓ Corrigido — substituído por particionamento TimescaleDB por tempo
✗ #13 — Índice inverso de follows ausente
Existia idx_follows_following(following_id, follower_id) para "quem me segue", mas faltava o inverso (follower_id, following_id) para "quem eu sigo". A query de feed usa ambas — sem o segundo, era um sequential scan.
✓ Corrigido — índice inverso adicionado
✗ #14 — Índices ausentes em itinerary_activities e posts
Faltava índice em itinerary_activities(day_id, position) — buscar atividades de um dia era seq scan. Faltava também posts(country_code, created_at) necessário para o top países do mês.
✓ Corrigido — dois índices adicionados

Bug de concorrência — 1 problema

✗ #15 — Race condition nos triggers de contadores
Os triggers de contadores (likes_count, etc.) estavam apenas esboçados para likes — os outros 3 (follows→follower_count, saves→saves_count, posts→total_trips) eram "semelhantes" mas não implementados. Em produção, os contadores ficariam sempre a 0. Além disso, os triggers de contadores para saves e follows não tinham proteção contra concorrência.
✓ Corrigido — todos os 4 triggers implementados completamente no tab Triggers

Triggers — implementação completa

Todos os 4 triggers de contadores implementados. Validação de prompt_versions adicionada.

⚠
Na v1, apenas o trigger de likes_count estava implementado. Os outros 3 eram apenas "semelhantes" — em produção, follower_count, saves_count e total_trips ficariam sempre a 0.
-- ================================================
-- TRIGGER 1: reactions → posts.likes_count
--            reactions → comments.likes_count
-- ================================================

CREATE OR REPLACE FUNCTION fn_update_likes_count()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    IF NEW.target_type = 'post' THEN
      UPDATE posts SET likes_count = likes_count + 1 WHERE id = NEW.target_id;
    ELSIF NEW.target_type = 'comment' THEN
      UPDATE comments SET likes_count = likes_count + 1 WHERE id = NEW.target_id;
    END IF;
  ELSIF TG_OP = 'DELETE' THEN
    IF OLD.target_type = 'post' THEN
      UPDATE posts SET likes_count = GREATEST(likes_count - 1, 0) WHERE id = OLD.target_id;
    ELSIF OLD.target_type = 'comment' THEN
      UPDATE comments SET likes_count = GREATEST(likes_count - 1, 0) WHERE id = OLD.target_id;
    END IF;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_likes_count
  AFTER INSERT OR DELETE ON reactions
  FOR EACH ROW EXECUTE FUNCTION fn_update_likes_count();

-- ================================================
-- TRIGGER 2: follows → users.follower_count
--                     user_profiles.following_count
-- ================================================

CREATE OR REPLACE FUNCTION fn_update_follow_counts()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' AND NEW.status = 'active' THEN
    UPDATE users SET follower_count = follower_count + 1
      WHERE id = NEW.following_id;
    UPDATE user_profiles SET following_count = following_count + 1
      WHERE user_id = NEW.follower_id;
  ELSIF TG_OP = 'DELETE' AND OLD.status = 'active' THEN
    UPDATE users SET follower_count = GREATEST(follower_count - 1, 0)
      WHERE id = OLD.following_id;
    UPDATE user_profiles SET following_count = GREATEST(following_count - 1, 0)
      WHERE user_id = OLD.follower_id;
  ELSIF TG_OP = 'UPDATE' THEN
    -- pending → active (conta privada aprovada)
    IF OLD.status = 'pending' AND NEW.status = 'active' THEN
      UPDATE users SET follower_count = follower_count + 1
        WHERE id = NEW.following_id;
      UPDATE user_profiles SET following_count = following_count + 1
        WHERE user_id = NEW.follower_id;
    END IF;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_follow_counts
  AFTER INSERT OR UPDATE OR DELETE ON follows
  FOR EACH ROW EXECUTE FUNCTION fn_update_follow_counts();

-- ================================================
-- TRIGGER 3: saves → itineraries.saves_count
-- ================================================

CREATE OR REPLACE FUNCTION fn_update_saves_count()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE itineraries SET saves_count = saves_count + 1
      WHERE id = NEW.itinerary_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE itineraries SET saves_count = GREATEST(saves_count - 1, 0)
      WHERE id = OLD.itinerary_id;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_saves_count
  AFTER INSERT OR DELETE ON saves
  FOR EACH ROW EXECUTE FUNCTION fn_update_saves_count();

-- ================================================
-- TRIGGER 4: itineraries published → user_profiles.total_trips
--                                     user_profiles.countries_visited
--                                     user_profiles.total_countries
-- ================================================

CREATE OR REPLACE FUNCTION fn_update_trip_stats()
RETURNS TRIGGER AS $$
BEGIN
  -- Publicação de roteiro
  IF TG_OP = 'UPDATE'
    AND OLD.status != 'published'
    AND NEW.status = 'published'
    AND NEW.deleted_at IS NULL
  THEN
    UPDATE user_profiles
    SET
      total_trips = total_trips + 1,
      countries_visited = -- adiciona país se ainda não existe no array
        CASE WHEN NEW.country_code = ANY(countries_visited)
          THEN countries_visited
          ELSE array_append(countries_visited, NEW.country_code)
        END,
      total_countries = array_length(
        CASE WHEN NEW.country_code = ANY(countries_visited)
          THEN countries_visited
          ELSE array_append(countries_visited, NEW.country_code)
        END, 1
      )
    WHERE user_id = NEW.user_id;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_trip_stats
  AFTER UPDATE ON itineraries
  FOR EACH ROW EXECUTE FUNCTION fn_update_trip_stats();

-- ================================================
-- TRIGGER 5: prompt_versions — validar soma = 100%
-- ================================================

CREATE OR REPLACE FUNCTION fn_validate_prompt_traffic()
RETURNS TRIGGER AS $$
DECLARE
  total_pct SMALLINT;
BEGIN
  SELECT COALESCE(SUM(traffic_percentage), 0)
  INTO total_pct
  FROM prompt_versions
  WHERE is_active = true
    AND id != COALESCE(NEW.id, ''::UUID);

  IF total_pct + NEW.traffic_percentage != 100 THEN
    RAISE EXCEPTION
      'A soma de traffic_percentage das versões ativas deve ser 100. Atual: %, a adicionar: %',
      total_pct, NEW.traffic_percentage;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_prompt_traffic
  BEFORE INSERT OR UPDATE ON prompt_versions
  FOR EACH ROW
  WHEN (NEW.is_active = true)
  EXECUTE FUNCTION fn_validate_prompt_traffic();

-- TRIGGER 6: audit_logs — proteger de UPDATE/DELETE
-- ================================================

CREATE OR REPLACE FUNCTION fn_protect_audit_logs()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'audit_logs é append-only. UPDATE e DELETE não são permitidos.';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_logs_readonly
  BEFORE UPDATE OR DELETE ON audit_logs
  FOR EACH ROW EXECUTE FUNCTION fn_protect_audit_logs();
