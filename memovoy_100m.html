Read replicas, multi-região mínima e disaster recovery para 100M

PostgreSQL: de 1 instância para CQRS com replicas

⚠
A partir de ~5M utilizadores ativos em simultâneo, uma única instância PostgreSQL começa a ser o bottleneck. A solução não é substituir o PostgreSQL — é adicionar read replicas e separar leituras de escritas (CQRS).

Multi-região mínima: EU + LATAM

ℹ
Para 100M com foco PT + BR, precisas de 2 regiões — não 4. EU (Frankfurt) serve Portugal e Europa. LATAM (São Paulo) serve Brasil. O routing inteligente leva cada utilizador à região mais próxima automaticamente.
🇪🇺 Região EU — Frankfurt
Utilizadores: Portugal, Espanha, Europa
Primary DB: PostgreSQL primary aqui
Dados: Todos os dados EU ficam aqui (RGPD)
Latência PT: ~10ms
🇧🇷 Região LATAM — São Paulo
Utilizadores: Brasil, América do Sul
DB: Read replica local + writes → EU via replicação
Dados BR: Ficam aqui por lei (LGPD)
Latência BR: ~15ms vs 200ms sem região local

Feed a escala: fan-out strategy

Como servir milhões de feeds personalizados por dia sem o sistema colapsar

⚠
O feed ML personalizado está definido mas a mecânica de como servir 100M feeds por dia é o maior bottleneck potencial do MemoVoy. Esta decisão de arquitetura afeta tudo: escala, custo, velocidade.

Os dois modelos opostos

Fan-out on Write

Quando alguém publica, o sistema escreve imediatamente no feed de todos os seus seguidores.

Feed sempre pronto — leitura instantânea
Baixa latência para o utilizador
Inviável para utilizadores com 1M+ seguidores
Fan-out on Read

O feed é calculado no momento em que o utilizador abre a app, juntando os posts de quem segue.

Funciona para qualquer número de seguidores
Dados sempre frescos
Lento quando o utilizador segue muitas pessoas

Solução: modelo híbrido (o que o MemoVoy deve usar)

Fan-out híbrido — baseado no número de seguidores
Publicação
Utilizador publica post
Sistema verifica: quantos seguidores tem este utilizador?
< 10k seg.
Fan-out on Write via Kafka
Escreve no feed Redis de cada seguidor. Rápido — a maioria dos utilizadores tem menos de 10k seguidores.
> 10k seg.
Fan-out on Read (creator mode)
O post é marcado como "creator content". Quando o seguidor abre o feed, este conteúdo é injetado em tempo real via query rápida, sem escrever em milhões de feeds.
# fan_out_service.py — Kafka consumer

async def handle_new_post(post_id: str, author_id: str):
    author = await get_user(author_id)

    if author.follower_count < 10_000:
        # Fan-out on write: escreve no feed de cada seguidor
        followers = await get_followers(author_id)
        pipeline = redis.pipeline()
        for follower_id in followers:
            pipeline.lpush(f"feed:{follower_id}", post_id)
            pipeline.ltrim(f"feed:{follower_id}", 0, 999)  # max 1000 posts
        await pipeline.execute()
    else:
        # Fan-out on read: apenas marca como creator content
        await redis.sadd("creator_posts:recent", post_id)
        await redis.expire("creator_posts:recent", 86400)  # 24h

async def get_user_feed(user_id: str, page: int = 0):
    # 1. Posts dos utilizadores normais que segue (já em cache)
    cached = await redis.lrange(f"feed:{user_id}", page*20, page*20+19)

    # 2. Posts de creators que segue (fan-out on read)
    followed_creators = await get_followed_creators(user_id)
    creator_posts = await get_recent_creator_posts(followed_creators)

    # 3. Merge + ML ranking
    merged = merge_and_rank(cached + creator_posts, user_id)
    return merged[:20]

Observabilidade: os 3 pilares

📊 Métricas
Datadog para todas as métricas de sistema e produto. Dashboards por serviço com RED metrics: Rate, Errors, Duration. Alertas com thresholds + PagerDuty para P1/P2.

Zero-Downtime Deployments

✗
A 100M utilizadores, um deploy com downtime é inaceitável — são potencialmente milhões de pessoas a receber erros em simultâneo. Dois padrões resolvem isto.
Blue/Green Deploy
Mantém dois ambientes idênticos (blue e green). O novo código é deployed no ambiente inativo. O traffic switch é instantâneo. Rollback em segundos se algo falhar.
Rollback instantâneo
Zero downtime garantido
Custo duplo de infra durante deploy
Canary Deploy (recomendado)
Nova versão lançada para 1% dos utilizadores. Se os SLOs se mantiverem, expande para 5%, 25%, 100%. Qualquer degradação reverte automaticamente.
Risco mínimo
Dados reais de validação
Rollback automático por SLO
# .github/workflows/deploy.yml — Canary automático
steps:
  - name: Deploy canary (1%)
    run: kubectl set image deployment/api api=memovoy/api:$VERSION
         kubectl annotate deployment/api canary.weight=1

  - name: Monitor SLOs por 10 minutos
    run: |
      for i in $(seq 1 10); do
        ERROR_RATE=$(datadog metric query "error_rate{service:api}")
        if [ $ERROR_RATE -gt 1 ]; then
          kubectl rollout undo deployment/api
          exit 1  # Deploy revertido automaticamente
        fi
        sleep 60
      done

  - name: Expandir para 100%
    run: kubectl annotate deployment/api canary.weight=100

# Implementação: routing de dados por região do utilizador

class DataResidencyRouter:
    REGION_MAP = {
        'PT': 'eu-central-1',   # Frankfurt
        'ES': 'eu-central-1',
        'FR': 'eu-central-1',
        'BR': 'sa-east-1',      # São Paulo
        'DEFAULT': 'eu-central-1'
    }

    def get_db_for_user(self, user_country: str) -> str:
        region = self.REGION_MAP.get(user_country, 'DEFAULT')
        return f"postgresql://{region}.db.memovoy.com"
